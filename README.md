# Интернет-магазин «Web-Larёk»

«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component

Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`

#### Класс Api

Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter

Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` - хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

### Данные

Приложение работает с двумя сущностями, которые описывают данные: товар и покупатель. Описываются следующими интерфейсами:

Товар:
interface Product {
id: string;
title: string;
description: string;
image: string;
category: string;
price: number | null;
}

Покупатель:
interface IBuyer {
payment: " 'card' | 'cash' ";
address: string;
email: string;
phone: string;
}

**Запрос на оформление заказа**
Описывает структуру данных, отправляемых на сервер при создании заказа.

| Поле      | Тип                | Назначение                                               |
| :-------- | :----------------- | :------------------------------------------------------- |
| `payment` | `'card' \| 'cash'` | Способ оплаты (унаследовано от `IBuyer`)                 |
| `address` | `string`           | Адрес доставки (унаследовано от `IBuyer`)                |
| `email`   | `string`           | Email для связи (унаследовано от `IBuyer`)               |
| `phone`   | `string`           | Телефон для связи (унаследовано от `IBuyer`)             |
| `total`   | `number`           | Итоговая сумма заказа                                    |
| `items`   | `string[]`         | Массив идентификаторов товаров (ID), выбранных в корзине |

Запрос на оформление заказа:
export interface OrderRequest extends IBuyer {
total: number;
items: string[];
}

**Ответ сервера на оформление заказа**
Описывает структуру данных, возвращаемых сервером после успешной отправки заказа.

| Поле    | Тип      | Назначение                                     |
| :------ | :------- | :--------------------------------------------- |
| `id`    | `string` | Уникальный идентификатор созданного заказа     |
| `total` | `number` | Итоговая сумма заказа, подтверждённая сервером |

Ответ на оформление заказа:
export interface OrderResponse {
id: string;
total: number;
}

**Ответ сервера со списком товаров**
Описывает структуру данных, получаемых при загрузке каталога товаров.

| Поле    | Тип         | Назначение                           |
| :------ | :---------- | :----------------------------------- |
| `items` | `Product[]` | Массив товаров, полученных с сервера |
| `total` | `number`    | Общее количество товаров в каталоге  |

Ответ со списком товаров:
export interface CatalogResponse {
items: Product[];
total: number;
}

**Интерфейс взаимодействия с API**
Описывает минимальный контракт, которому должен соответствовать класс для работы с сетью. Позволяет подменять реализацию (например, для тестирования).

| Метод  | Параметры                                                    | Возвращаемое значение | Назначение                                                                                                            |
| :----- | :----------------------------------------------------------- | :-------------------- | :-------------------------------------------------------------------------------------------------------------------- |
| `get`  | `uri: string`                                                | `Promise<T>`          | Выполняет GET-запрос по указанному URI и возвращает промис с данными ответа.                                          |
| `post` | `uri: string`<br>`data: object`<br>`method?: ApiPostMethods` | `Promise<T>`          | Отправляет POST-запрос (или другой указанный метод) по URI с переданными данными. Возвращает промис с данными ответа. |

Api:
export interface IApi {
get<T extends object>(uri: string): Promise<T>;
post<T extends object>(
uri: string,
data: object,
method?: ApiPostMethods,
): Promise<T>;
}

### Слой коммуникации

Для взаимодействия с внешним API сервера "веб-ларёк" используется класс `ServerConnector`.

### Назначение

Класс изолирует модели данных от деталей сетевого взаимодействия. Он отвечает за:

- Получение списка товаров с сервера.
- Отправку заказа на сервер.
- Обработку ошибок сети (единым образом).

### Композиция

Класс `ServerConnector` будет использовать композицию, чтобы выполнить запрос на сервер с помощью метода get класса Api и будет получать с сервера объект с массивом товаров.

### Класс LarekApi

Утилитарный класс, отвечающий за подготовку данных о товарах перед передачей их в модель. Не является базовым классом: работает с сущностью текущего проекта (товаром), поэтому не может быть перенесён в другой проект без изменений — в отличие от действительно базовых классов (`Api`, `Component`, `EventEmitter`), которые никак не связаны с бизнес-логикой конкретного приложения.

**Назначение:**
Сервер возвращает у товара только имя файла изображения (например, `1.svg`), без полного пути. Класс дополняет это имя базовым адресом CDN (`CDN_URL`), формируя полную ссылку, пригодную для вставки в атрибут `src` тега `<img>`.

**Конструктор:**

```typescript
constructor();
```

Параметров не принимает.

**Методы:**
| Метод | Параметры | Возвращаемое значение | Назначение |
| :--- | :--- | :--- | :--- |
| `prepareProducts` | `data?: { total: number, items: any[] }` (опционально) | `Product[]` | Принимает ответ сервера с массивом товаров (`CatalogResponse`), проходит по каждому товару и, если у него указано изображение, приводит поле `image` к полному URL, добавляя к имени файла `CDN_URL`. |

`LarekApi` используется на этапе загрузки каталога — вызывается внутри `AppPresenter.init()`, между получением сырого ответа от `ServerConnector.fetchCatalog()` и сохранением товаров в `CatalogModel.setProducts()`.

### События моделей данных

Все события моделей генерируются без данных — уведомляют только о факте изменения. Актуальные данные Презентер запрашивает напрямую у модели через её методы в момент обработки события — модель является единственным источником истины.

| Событие            | Когда генерируется                         |
| :----------------- | :----------------------------------------- |

| `basket:changed`   | товар добавлен, удалён или корзина очищена |
| `customer:changed` | обновлены или очищены данные покупателя    |

| Событие           | Когда генерируется                                              | Данные                                                                                                                           |

## Презентер

Реализован отдельным классом `AppPresenter` — такой подход выбран для более чёткого разделения ответственности. Файл `main.ts` отвечает только за композицию: создаёт экземпляры моделей, представлений, шаблонов разметки и коннектора к серверу и передаёт их в презентер. `AppPresenter` берёт на себя всю логику взаимодействия между слоями приложения, включая первичную загрузку каталога с сервера — реализована в публичном методе `init()`, который вызывается из `main.ts` сразу после создания презентера.

Зависимости (брокер событий, модели данных, представления, коннектор к серверу, шаблоны разметки, вспомогательный класс `LarekApi`, статичная карточка превью `previewCard`) передаются в конструктор `AppPresenter` единым объектом. Презентер не создаёт свои зависимости самостоятельно и не содержит импортов конкретных реализаций верхнего уровня сборки — работает с уже готовыми экземплярами через их типы, что снижает связанность между `main.ts` и внутренней логикой презентера.

Презентер только подписывается на события через `events.on(...)` в едином методе `subscribe()` и не генерирует собственных событий. Каждому событию соответствует один обработчик, вызывающий методы моделей для изменения данных либо методы представлений для перерисовки. Обработчики отправки форм (`order:submit`, `contacts:submit`) не производят повторную валидацию данных — это уже гарантировано тем, что кнопка отправки физически заблокирована, пока данные невалидны.

Все шаблоны разметки (`<template>`) находятся один раз при старте приложения в `main.ts` и передаются презентеру или напрямую компонентам представления готовыми — сам поиск в разметке (`document.getElementById`/`querySelector`) при каждом рендере не производится, вместо этого используется клонирование уже найденного шаблона (`cloneTemplate`).

Карточка подробного просмотра товара (`ModulProductCard`) создаётся один раз глобально в `main.ts`, так как описывает статичный блок разметки — при каждом открытии превью презентер лишь вызывает её `render()` заново с актуальными данными, не пересоздавая экземпляр. Карточки каталога (`CatalogCard`) и корзины (`CartItemCard`), напротив, создаются заново при каждом рендере соответствующего списка — их может быть несколько одновременно.

Формы оформления заказа (`OrderForm`, `ContactsForm`) создаются заново при каждом открытии своего шага — так они гарантированно начинают работу с чистой разметкой без необходимости отдельного сброса значений. Презентер хранит ссылку на текущий открытый экземпляр формы (`currentOrderForm`, `currentContactsForm`) и при каждом изменении данных покупателя обновляет уже показанную форму через `render()`, не пересоздавая её — это нужно, чтобы визуальные изменения (подсветка выбранного способа оплаты, текст ошибок) отображались на уже видимой пользователю форме, а не на новом, невставленном в DOM экземпляре.

Презентер содержит несколько вспомогательных приватных методов (`renderGallery`, `renderBasket`, `renderPreview`, `renderOrderForm`, `renderContactsForm`), которые собирают актуальную разметку конкретного компонента на основе текущих данных моделей. Они вынесены отдельно, так как переиспользуются в нескольких обработчиках, и позволяют избежать дублирования кода сборки представления.
